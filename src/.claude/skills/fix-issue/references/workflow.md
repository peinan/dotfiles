# fix-issue 詳細ワークフロー

## Phase 1: Issue 理解

### 1.1 Issue 取得

```bash
gh issue view <番号> --json title,body,labels,comments,assignees,state
```

### 1.2 分析チェックリスト

- [ ] 問題の本質を一文で説明できるか
- [ ] 再現手順が明確か（なければユーザーに確認）
- [ ] 期待される動作が定義されているか
- [ ] 成功基準を設定したか

### 1.3 出力

Issue サマリーを作成:
- タイトル
- 問題の要約
- 成功基準

## Phase 2: コードベース調査

### 2.1 キーワード抽出

Issue から以下を抽出:
- ファイルパス・ファイル名
- 関数名・クラス名
- エラーメッセージ
- 設定キー・環境変数

### 2.2 Explore エージェント活用

```
Explore エージェントに以下を依頼:
- キーワードに関連するファイルの特定
- 影響範囲の分析
- 既存の類似パターンの発見
```

調査の深さ: "詳細" を指定

### 2.3 セキュリティ評価

以下に該当する場合は注意フラグを立てる:
- 認証・認可 (auth)
- 決済・課金 (payments)
- インフラ・設定 (infra)
- 個人情報 (PII)

### 2.4 出力

調査結果サマリー:
- 関連ファイル一覧（パス付き）
- 影響範囲
- セキュリティ注意事項（該当する場合）

## Phase 3: プラン作成

### 3.1 アプローチ列挙

最低2つの解決アプローチを検討:
- アプローチ A: [説明]
- アプローチ B: [説明]

### 3.2 Tradeoff 分析

各アプローチについて:
- メリット
- デメリット
- 影響範囲
- 工数感（大/中/小）

### 3.3 推奨選択

推奨アプローチを選択し、理由を明記。

### 3.4 実装ステップ

1. [ステップ1]: [詳細]
2. [ステップ2]: [詳細]
3. ...

### 3.5 テスト計画

- [ ] 手動テスト項目
- [ ] 自動テスト（該当する場合）
- [ ] エッジケース確認

### 3.6 出力

プランドキュメント:
- 推奨アプローチ
- 実装ステップ
- テスト計画
- セキュリティ考慮事項

## Phase 4: ユーザー承認

### 4.1 プラン提示

作成したプランを提示。

### 4.2 確認事項

以下を確認:
- プランに同意するか
- 追加の要件・懸念点はあるか
- 変更のスコープは適切か

### 4.3 承認待ち

明示的な承認があるまで実装に進まない。

## Phase 5: 実装

### 5.1 コード変更

プランに従って変更を実行。

### 5.2 セキュリティチェック

セキュリティ注意フラグがある場合:
- 変更箇所を再確認
- 脆弱性がないか検証

### 5.3 テスト実行

テスト計画に従って検証。

### 5.4 完了報告

- 変更内容のサマリー
- テスト結果
- 追加の注意事項（あれば）

## エッジケース対処

### Issue が不明確な場合

1. 不明点をリスト化
2. AskUserQuestion で確認
3. 確認後に Phase 2 へ進む

### 関連ファイルが見つからない場合

1. キーワードを拡張して再検索
2. ユーザーにヒントを求める
3. README やドキュメントを参照

### 複数の Issue が関連している場合

1. 関連 Issue を確認: `gh issue list --search "related keywords"`
2. 依存関係を整理
3. 優先順位を確認
